# Performance

Targets (plan §24): full sync of a 2,000-file source under 5 minutes; incremental sync of 20 changed files under 30 seconds; Explore pages under 1 second at p95.

## Test environment (recorded, because a number without one means nothing)

| | |
|---|---|
| CPU | Intel(R) Xeon(R) Processor @ 2.10GHz × 4 |
| RAM | 16 GiB |
| OS | Linux 6.18.44-fc-v50 |
| Node | v22.22.2 |
| PostgreSQL | PostgreSQL 16.13 (local, same machine) |
| Network | loopback only: GitLab is faked in-process, so no network latency is included |
| Concurrency | 1 sync at a time; queries sequential; PostgreSQL local, pool of 3 |
| Fixture | deterministic synthetic repository generated by `scripts/perf.ts`: 2000 files (about 70 % classes, 15 % procedures, 12 % test classes, schema, requirements and one process, docs), 4119 relationships, 300 commits; 20 classes modified for the incremental run |

## How to read this
- **GitLab is faked in-process.** A real sync adds the archive download and per-commit diff requests, which will usually dominate. The parse → persist → activate path (what Lens itself controls) is what is measured here.
- The synthetic repository has fewer relationships per file than a mature codebase; the harness is repeatable (`npm run perf`, `PERF_FILES=…`) so you can measure your own repositories' size class on your hardware. Results are written to `docs/perf-last-run.json`.
- Explore queries rebuild their view per request (about 200 ms at this size); the immutable-snapshot graph is cached, the imported history overlay is not.
- One run on one machine: treat as order of magnitude, not a benchmark.
